# 选型调研报告

日期：2026-11-12。本报告记录每个环节选了什么、为什么、比较过哪些选项，以及性能基线。

事实分三类，文中都标了出来：

- **实测**：当天在本机跑出来的结果。
- **读到**：官方文档、代码仓库或包元数据的原文，逐条来源在附录的两份原始笔记里。
- **推断**：根据读到的内容做的判断，没有直接验证。

## 1. 结论一览

| 环节 | 选择 | 比较过的选项 | 主要理由 |
|---|---|---|---|
| 数据 | Tushare Pro 为主，BaoStock 对账 | AKShare、聚宽、米筐、掘金、通达信、adata、Qlib 社区数据、中证官网 | 现有密钥实测覆盖全部所需数据；BaoStock 是免费的独立来源 |

## 2. 调研方法

**联网调研**两路并行，分别核实数据源和框架的现状（维护状态、价格、许可证、版本支持、覆盖范围）。原始笔记见附录，共约 950 行，每条事实附来源链接。

**本机实测**的环境是 macOS arm64、Python 3.13.13、pandas 3.1.1、numpy 2.5.4：

1. 依赖解析：34 个候选包逐个测试能否与 pandas ≥ 3.1.1、numpy ≥ 2.5.4 在 Python 3.13 下解析出一组版本。只有 Qlib 失败。注意「能解析」不等于「能用」：没写版本上限的旧包也会解析成功，zipline-reloaded 就是退回到了一个没写上限的旧版本。
2. 安装并运行最小示例：alphalens-reloaded、quantstats、rqalpha、vnpy、cvxpy、duckdb、polars、pyarrow、scikit-learn、lightgbm、backtrader、backtesting.py。
3. BaoStock：登录后实际取了日线、证券列表、退市股行情、指数成分、复权因子、财务、业绩预告和快报、分红、行业。
4. Tushare：用现有密钥逐个调用 26 个接口，并补测了退市股行情、指数权重的历史范围、各数据集的最早日期。

### 3.2 选择与理由

- **Tushare 为主**：现有密钥已经能调通所需的全部接口（见 3.3），不需要新增费用；可以按交易日一次取全市场，下载效率高；本地落盘没有限制条款。
- **BaoStock 对账**：免费、不用注册，数据来源独立。ST、停牌、退市这类标记一旦错了回测结果就不可信，用第二个来源抽样核对。
- **米筐是升级路线**：它是唯一提供严格时点财务和日度指数权重的，如果以后发现 Tushare 的这两个缺口影响结论，再去试用。

### 3.3 Tushare 实测结果

26 个接口通过 25 个：交易日历、证券列表（在市 5580 只、退市 343 只）、日线、复权因子、每日指标、涨跌停价、停复牌、曾用名、ST 名单、指数日线、指数权重、申万行业成分、利润表、财务指标、业绩预告、业绩快报、分红送转、卖方盈利预测、增减持、回购、资金流向、分钟线。没通过的一个是积分查询（接口名不对），所以积分余额和到期日没有查到。

补测的几项：

- 退市股的日线和复权因子能取到（新都退 2015–2017、邯郸钢铁 2008–2009）。
- 指数权重是月末快照。最早日期：沪深 300 为 2005-04，中证 500 为 2007-01，中证 1000 为 2014-10，中证 2000 为 2023-08。指数发布之前没有成分。
- 涨跌停价从 2007-01-04 起才有；ST 名单、停复牌、每日指标在 2010 年以前都有数据。
- 利润表同一报告期会返回多个版本，用 `update_flag` 区分。

### 3.4 BaoStock 实测结果

数据更新到前一个交易日。日线自带 `tradestatus` 和 `isST`；证券列表里有退市标记和退市日期，退市股行情能取到；沪深 300、中证 500 的成分可以按任意历史日期查询；财务数据带 `pubDate`；业绩预告和快报带公告日。全量证券列表一次要 17 秒，接口是串行的，不适合做主力下载。

### 3.5 已知缺口

1. 指数权重只有月末快照，月中的权重要自己用价格推算。
2. 财务数据更正前的历史版本不完整，时点财务只能做到「按实际公告日生效」。
3. 没有现成的分析师一致预期，只有逐篇研报的预测，要自己聚合。
4. 复权因子和市值没有版本记录，数据源事后修正了也看不出来。

### 4.2 为什么不用 backtrader

以前用它做单标的择时（比如 MACD）是合适的，换成截面选股有三个问题：

1. **结构不合适**。它为每个标的维护一路数据，每根 K 线逐路调用 Python 代码。5000 只股票 × 4000 个交易日就是两千万次 Python 层的回调，这是慢的来源。实际慢多少见 4.6 的实测。
2. **没有 A 股规则**。T+1、涨跌停、停牌、最低佣金、整手都要自己写佣金类、下单过滤和仓位计算；分红送转只能喂复权价。
3. **已经停更**。最后一版是 2023-04，声明支持的 Python 只到 3.7。

### 4.3 为什么不用 backtesting.py

它的 `Backtest` 只接收一张行情表，也就是一个标的（实测，0.6.6）。库里有一个 `MultiBacktest`，但它做的是把同一个策略分别在多个标的上各跑一遍，互相独立，没有共用的资金和持仓。截面选股需要的是「一笔钱在几千只股票里分配」，这个模型它表达不了。它适合的是单标的的信号策略和参数优化。

### 4.4 为什么 rqalpha 只做对账

它的 A 股规则是所有候选里最全的，而且官方支持 Python 3.13 和 pandas 3，所以用它做独立的正确性核对。不当主引擎有两个原因：它是事件驱动的，批量检验上千个因子太慢；许可仅限个人或非营利机构的非商业使用，以后如果用途变了会受限。另外免费数据包每月才更新一次，日更需要付费或者自己写数据源。

### 4.5 最接近的现成方案：vectorbt

vectorbt 是向量化的，核心用 numba 编译，1.x 起还有可选的 Rust 引擎，速度上是现成方案里最强的；它支持多标的共享现金、整手粒度和比例费用。缺的是最低佣金、涨跌停和停牌约束、分红送转、未成交顺延，这些要用 numba 回调自己写，更完整的功能在它的付费版里。许可带 Commons Clause，个人研究不受影响。

它是自研引擎最直接的比较对象：如果自研的不比它快、规则又没有更全，就没有自研的必要。4.6 会把两者放在同一个任务上比。

### 4.6 性能实测（基线）

基线日期 2026-11-12，Apple Silicon 15 核，Python 3.13。完整矩阵（160 行，含内存、首次调用、口径说明）在 [BENCHMARKS.md](BENCHMARKS.md)，原始样本在 `bench/results/compare.json`。**测量时机器上有其他任务在跑**：量级差距可信，30% 以内的差距要等空闲时用 `make bench-compare` 重测后再下结论。之后每次改动引擎，都与这里的基线比较。

**一次回测的耗时**（4000 个交易日 × 5500 只股票，约 100 只持仓，单线程，输入已准备好；精确实现的逐日净值与 `panelbt` 相差不超过 1e-9）：

| 实现 | 每 21 日调仓，比例佣金 | 相对 panelbt | 每 21 日调仓，整手加现金缩减 | 每日调仓 |
|---|---:|---:|---:|---:|
| **panelbt（Rust 内核）** | **2.7 ms** | 1 | **2.5 ms** | **27.6 ms** |
| 手写 NumPy，逐日，稀疏持仓 | 9.0 ms | 3.3 倍 | 8.0 ms | 80.7 ms |
| 手写 NumPy，逐日，全截面 | 14.5 ms | 5.4 倍 | 14.2 ms | 191 ms |
| 手写 NumPy，整块近似（费用口径有近似） | 59.9 ms | 22 倍 | 做不了 | 71.0 ms |
| Polars，整块近似（同上） | 258 ms | 96 倍 | 做不了 | 242 ms |
| vectorbt 1.2.1（Numba） | 1.20 s | 443 倍 | 0.99 s | 2.82 s |
| vectorbt 1.2.1（Rust 引擎） | 1.29 s | 477 倍 | 做不了 | 1.70 s |
| bt 1.4.1 | 7.4 s | 2760 倍 | 3.6 s | 44.8 s |
| 纯 Python 参考实现（自己写的，用来对拍） | 17.3 s | 6400 倍 | 14.9 s | 21.0 s |
| backtrader 1.9.78 | 330.8 s | 12.3 万倍 | 278.5 s | 335.6 s |

- **完整 A 股规则**（涨跌停、停牌、T+1、最低佣金、分红送转、退市、未成交顺延）只有 `panelbt` 和参考实现能跑：3.2 ms 对 17.5 s。第三方引擎和整块向量化写法都表达不了这组规则，所以没有可比的对手。
- **峰值内存**（同一场景）：`panelbt` 0.47 GB，backtrader 3.0 GB，vectorbt 8.4 GB。
- **1000 组小面板批量**（1000 日 × 100 只，15 线程）：`panelbt` 56 ms，手写 NumPy 全截面 93 ms，NumPy 整块近似 53 ms，vectorbt 1.08 s，bt 32 s，backtrader 140 s。

**不占优的地方**（如实记录，是后续优化的对象）：

1. **含输入校验的口径下，`panelbt` 比手写 NumPy 慢**：单次 20.5 ms 对 8.1 ms，1000 组批量 341 ms 对 84 ms。慢在 Python 侧的行情和目标校验（约 18 ms），不在内核。同一份行情反复回测时校验只需做一次，这部分还没做成可复用。
2. 小面板上手写 NumPy 与 Rust 内核同量级（上面的 56 ms 对 53–93 ms）；Rust 的优势在全市场规模和完整规则上。
3. 完整规则的自测场景是 3.8 ms，没有达到 2 ms 的目标（公司行为按日索引尚未做）。

**其余内核的 Rust 与基线对比**（各自的完整表见对应文档）：

| 环节 | 基线 | Rust | 结论 |
|---|---|---|---|
| 模拟盘行情接收与撮合，5500 行一批 | Python 循环 1.67 ms；NumPy 0.125 ms | 0.064 ms | 用 Rust（基线只做了行情接收，没有撮合） |
| 风险模型截面回归，4000 日 × 5500 × 45 | NumPy SVD 11.8 s；NumPy Gram 单线程 3.0 s、4 线程 1.6 s | 单线程 5.0 s；15 线程 0.64 s | 多线程用 Rust；**单线程 Rust 比 NumPy Gram 慢** |
| 特质风险（EW 加 NW） | NumPy 0.120 s | 单线程 0.147 s；15 线程 0.019 s | 多线程用 Rust |
| 因子协方差（45 × 45） | NumPy 0.7 ms | 0.6 ms | 没有差别，短面板留在 NumPy |
| 组合优化单次求解，N = 5000 | CVXPY 加 Clarabel 209 ms；直接调 Clarabel 192 ms | 194 ms | 同一个求解器，单次不用 Rust；200 个独立问题并行时用 Rust（9.7 s） |
| 组合优化的约束写法（不是语言问题） | 约束写在 N 维上 368 ms | 写在 K 维因子暴露上 186 ms | 改写法快一倍 |
| 数据层长表落到稠密面板，4800 × 5900 | Polars 10.1 s | NumPy 0.09 s | NumPy 已经够快，不写 Rust |
| 因子算子 `panelops`（第一轮，34 个算子） | bottleneck / NumPy / Polars | 默认 15 线程在 600 组配置里 556 组最快；**单线程有 16 个算子更慢**（如滚动标准差 505 ms 对 bottleneck 75 ms） | 返工中：内核改成逐行流式，单线程不慢于最快基线才合并 |

| 组合优化 / 风险 | skfolio | 备选。有通用的 Barra 式因子模型，能否适配全 A 没有验证 |
| 绩效 | quantstats 0.0.86 | 采用。实测在 pandas 3.1 下能出指标 |
| 绩效 | pyfolio-reloaded、empyrical-reloaded | 备选。声明支持 pandas 3.0–3.1 |
| 风险模型 | GitHub 上的 A 股 Barra 仓库 | 不用。都是 2018–2025 年的个人项目，没有许可证文件 |

### 5.4 实盘接入

QMT 的 Python 库 xtquant 只能在 Windows 上运行，而且要先启动券商的 MiniQMT 客户端；PTrade 托管在券商机房，各家版本不同。研究环境在 macOS 上，实盘要另配一台 Windows 机器，这一轮不做。

## 6. 许可与使用限制

- **Tushare**：许可是个人的、非商业用途的；账号不得出租或分享。本地落盘没有禁止条款。
- **rqalpha**：仅限个人或非营利机构的非商业使用。本项目只把它当开发期的对账工具。「用自己的钱实盘」算不算商业目的，许可文本没有明说。
- **vectorbt、PyBroker**：Apache 2.0 加 Commons Clause，不能把基于它们的功能包装成收费服务。
- **backtrader（GPLv3+）、backtesting.py（AGPL-3.0）**：只在性能对比里作为独立进程运行，不链接进自研的包。

## 7. 没有核实的事项

4. Tushare 权限到期后，已下载的数据能否继续离线使用（协议没写）。
5. hikyuu、AKQuant、riskfolio-lib、alphainspect 在 pandas 3.1 下的实际表现。
