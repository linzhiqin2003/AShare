# C1：加密货币内核实现记录

范围为 DESIGN 4.17 v3.1 内核第 1–6 条和 C1 输入合同。没有修改 `src/ashare/`、
设计稿、真实数据目录；没有提交或推送。内核不新增市场档案和调度层。

## 实现中的选择

1. **最小名义的价格来源**：`min_notional` 要求同时给 `Liquidation.mark_open`，
   没有这个来源就报错。不能把普通成交价假装为标记价。资金费、维持率、数量步长和
   最小数量均可独立开启；它们也支持已有的混合账户。
2. **权重换算**：开启强平后，分子使用按标记开盘估值的权益，分母使用标记开盘价
   乘固定乘数；费用及成交价偏离标记价的浮亏完整进入候选开仓检查。无论通用账户是否
   允许融资，交易所初始保证金都必须由合约权益满足。
3. **清算费名义**：按含滑点和冲击的有效强平成交价计算。先合计所有列的应收，
   再按账户正余额封顶，按各列应收的比例分配实际费用到贡献；穿仓信用只计账户级
   `bankruptcy_deficit`，不伪装成单个证券的利润或外部入金。
4. **无法报价的强平**：忽略普通交易掩码、参与率、步长和数量门槛，但正常冲击模型
   仍需要有效成交量。强平成交价无效时直接报错；不虚构价格或无限流动性。
5. **维持率独立使用**：没开 `Liquidation` 时仍使用旧的收盘追保／下一行减仓机制，
   维持率只改触发阈值，修复目标仍是初始保证金。不开启新输入则完全走旧算术路径。
6. **分档计数与容差**：每行最多计一次超限；盘中强平行按设计的保守约定计超限。
   开盘普通减仓的时点已知，不把它误当成盘中退出。λ 的终点比较沿用名义 × 1e-12
   的风险容差，落入这个容差的端点视为触线，λ 截到 1。
7. **旧输出兼容**：保留旧 `METRICS`／`EXTRA_COUNTERS`，另外定义
   `CRYPTO_METRICS`／`CRYPTO_COUNTERS`。无新输入时新增 Result 属性为 None，coverage
   不追加新键；开启时才返回数组和对应计数。保留已有冻结摘要和断言，没有重新冻结。
   无新输入的 DayRecord 保持原字段，开启时的 CryptoDayRecord 多三个日字段。
8. **快照**：写入格式 3，仍接受无新输入的格式 2。保留旧输出长度，恢复时对旧计数向量补零，
   CRC 和输入指纹仍先验证；新面板加入原有 full/sample 指纹。风险和资金费在本行
   `step` 的交易阶段读取，不在上次 `step` 的下一行 pre-open 提前读取。
9. **日历及数据质量**：内核没有时间戳或交易对名称，不推断 09:35 等事件。
   C3 把它对齐到下一整点，保留旧仓特殊规则未建模的完整影响区间，并输出实际使用
   范围。最大杠杆、缺失行情、结算价替代来源也由 C2/C3 检查和报告。
10. **数量门槛**：步长从零起算，最小数量只是阈值；最小 3、步长 2 时允许 4、6，
    不允许 3、5。全平零头在应用参与率上限后判断是否能全部平掉，再豁免数量规则。
11. **旧路径的成本隔离**：Rust 用编译期 `C=false` 消去新增逐行判断；保留旧日数组
    长度。Python 对已验证的普通标量保证金参数直接判断，不再为决定现金专用路径
    扫描其广播数组；数组形式仍走原有判断，账户计算及校验不变。
12. **交割与下架**：复用已有到期路径，不新增交割价格字段，也不改旧路径的价格、
    盈亏和费用计算。C3 将到期行 settlement 置为交割／下架结算价，并显式给
    `delivery_fee_rate=当时吃单费率`、按张费用 0；内核不隐式复制普通手续费参数。
13. **R1 的意图检查**：未持仓、目标非零、有效执行报价且方向掩码开启时，先验证
    三个标记价，再做权重换算、数量和资金过滤。不能因为预计开不起或最终取整为零
    而隐藏缺失的必需数据；无持仓且到期已过、无报价、方向掩码关闭或目标为零时
    允许 NaN。零权益不开仓，但不额外记爆仓；后续入金可使未爆仓账户恢复。
    不可交易列缺标记价时，按既有合同使用上一行 settlement（首行用当行有限值）
    作为受阻分类的数量占位；挂起的仍是原始目标，不是按占位价计算的张数。
14. **R1 的受阻分类**：按原因记录价格／方向掩码／成交量受阻，普通无效冲击报价
    也是价格受阻。纯数量／资金过滤是本次决策的结束；二者并存时，实际存在的市场
    受阻原因仍允许保存原目标。这不依赖最终成交量与请求量是否相等。

## 设计问题

- 新增 `min_notional` 单独存在时没有指定标记开盘价的输入通道。当前按第 1 条报错，
  将来若需“有最小名义、没有交易所强平”的账户，可另行设计独立标记价格输入。
- 七步里的风险检查都以“还有持仓”为前提。若交割费把最后一个已到期仓位的余额扣成
  负数，或者关闭阶段融资利息造成负余额，设计没有明确是否同样获得穿仓信用。
  当前只在交易所强平成交后发放信用；交割／利息负余额保留债务并锁存破产，
  不因后续入金恢复开仓，也不把这类债务无依据地转给保险基金。
  这是模型边界，不能把合约 cash 当作真实可转出钱包余额。
- 在第一档模型中，任意盘中强平都使分档覆盖按不确定处理，严格 C3 应拒绝这一行。
  这是设计 v3.1 指定的保守代价；内核保留强平数值，同时给出超限诊断，没有放宽它。
- **R1 组合要求的顺序边界**：成交后强平清空全账户，发生在本行交割与资金费之前，
  所以“成交后强平、同一行实际交割释放保证金且实际扣资金费”不可能同时发生。
  保持 DESIGN 的七步顺序：该类测试断言待发生的交割和资金费被取消；收盘强平
  组合则断言交割已释放保证金、已扣资金费后才强平。报告分别命名为
  `expiry_suppressed/funding_suppressed` 和 `expiry_released/funding_debited`，
  不把存在非零输入当成已执行事件。这是验收措辞与事件顺序的边界，不改 DESIGN。

## 反例、错误与回归

- 先写 14 个确定性用例并用本 worktree 的旧扩展运行：全部因旧 API 无 `Liquidation`
  而无法表达；原始红灯记录为 `bench/results/crypto_red.txt`。
- R3 V1：现金 10、成交 100、标记 90 的整数开仓拒绝。另用现金 3、持仓 2、98
  减掉 1 的例子覆盖成交后 D=0，不再使用 v2 的错误“放行开仓再强平”预期。
- R1/R2：开盘跳空不能被目标或后续涨价救活；右边界资金费、强平后不收费；
  收费后按 settlement 再检查；交割直接用交割价；负余额无清算费；清空跨列挂起单。
- R3 V2/P2：分档用最高价，多列清算费合计后封顶；收费恰好归零不记爆仓。
- 开发中发现的可执行问题均补回归：零费用夹具漏设默认滑点（修夹具参数，不改手算
  期望）；交割后负余额未锁存破产（补“到期费留下债务、后来入金”反例）；
  复用现货数量格点会产生非法 3、5 张（增加 3/2 例）；独立数量规则在初次、
  参与率、资金缩量、减仓四处漏记取整为零（四个先失败的回归）；新增零输出改变旧
  冻结摘要（保留原测试，调整 API 仅在启用时暴露新结果）。
- 编译／格式检查捕获过调用点漏传行号及格式问题；已由 cargo/ruff 的整包检查守住。
- 追加混合账户语料发现参考实现的两处计数偏差，均先确认回归失败再修复，未改内核：
  seed 2 的现货可支付数量二分会比旧内核解析封顶多花 1 ULP，导致下一行提现计数
  不同；参考实现补独立的双费用区间解析上限，保留精确零计数。seed 76 的无效冲击
  报价被误记为数量过滤，将数量计数放回报价验证之前。回归分别固定 `2^-45` 的
  现金残差和“无效报价 1 次、数量取零 0 次”，没有放宽对拍断言。
- 没有修改任何原有测试断言，也没有新增跳过或放宽已有容差。

此前参考实现独立重算账本和 λ，却把“最终成交量不同就是受阻”“可支付只看候选账本”
等控制流程假设照搬了过去。两边因此同错，对拍只能证明一致，不能证明符合合同。
本轮在 SPEC 增加四条 `Ordinary-order decisions`，reference 按文字逐条判定：先枚举
价格／掩码／参与率原因，数量过滤另算；无效普通报价单列为受阻；先读实际权益、再
模拟候选交易；先验证可执行的非零意图、再换算权重。回归期望来自手算和明确的异常
语义，并分别约束原生、reference、step、逐行 snapshot 四种入口。额外对 reference
本身做真实变异，防止只变异 Rust 的对拍给出虚假的安全感。

组合用例各用 4 列、5 行，并镜像多空方向：第 0 行有挂起目标，第 1 行强平且清空
目标，第 2 行无新目标时保持空仓，第 3 行新目标重开。成交后强平手算余额为
`1.9 + 0.003 × side`，同一行待交割／收费被取消；收盘强平先交割第 3 列，手续费
0.1，资金费 `2×1.5 + 1×0.5 = 3.5`（到期列的 99 不收），再扣普通强平费 0.3 和
清算费 0.3，余额 **1.4**。下一次开仓另扣 0.1。每行比较全部账户状态和挂起目标，
包括存档恢复；最终所有输出及事件逐位一致。语料不仅计各子项，还要求
`post_trade.all_interactions`、`close.all_interactions` 在单个案例同时成立，各至少 2。
