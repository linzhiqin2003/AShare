### P-010 求值器少复制：字段叶子不再预先改写、无缓存时不算缓存键

- 提交：`b746a78`；复核后修补 `21e6b71`。
- 手段：硬件（少读写内存、少做无用功）。
- 先量（批量入口，全面板，按节点类别的「数据量 / 耗时」）：逐元素算子平均 5.8 ms 读写 3 张 229 MB 面板，约 118 GB/s，贴着本机约 135 GB/s 的带宽上限，不再压；`cs_rank` 27 ms、`ts_mean` 15–20 ms 是排序和补偿求和的计算量，不是复制（新开 229 MB 输出并写满 1.8 ms，与写一张已触及的面板 1.7 ms 相同，分配本身不是瓶颈）。离带宽最远、又纯属复制的是字段叶子准备：每个叶子单线程 `isfinite` 加 `where` 复制约 14 ms（读写约 0.75 GB，约 53 GB/s）；剖析里 `_compute` 自身 0.78 s，几乎全是它。另有每个表达式在没有缓存目录时也对 4824 个日期和 5923 个代码做 JSON 加 SHA-256 算缓存键，95 个共 0.15 s。
- 改动：
  1. 浮点字段叶子作为算子输入时直接把（连续的 float64）原数组交给内核，不再先把非有限值和掩码外的格子改写成 NaN。Rust 内核对每个输入格子都按「非有限即缺失」处理（逐元素：`is_finite` 判定、输出再过一遍 `is_finite`；时序：`values()` 与延迟的 `is_finite`；截面：`Panel::x`、暴露与权重的 `is_finite`），掩码随每次调用一并传入（字段是数组，逐元素调用也总带掩码），所以结果逐位相同。字段本身就是结果时（根）照旧改写；配置了 NumPy 分派（`panelops.api.BACKENDS` 非空）时也照旧改写，不依赖 NumPy 候选实现的缺失规则；整数行业字段照旧。
  2. 没有缓存目录时不计算缓存键（键只用于定位缓存文件）。
- 逐元素链融合：图里 158 个逐元素节点中有 59 个是「只有一个逐元素消费者、又不是结果」的中间值，融合成一遍扫描最多省它们各一次写加一次读，按 5.8 ms × 2/3 估约 0.2 s（批量 5.4 s 的 4%）。这一项要在 Rust 里另写一套保证逐位相同的逐元素解释器，本提交没有做，留作后续（见末尾）。

- 一致性：全面板 95 个结果整体摘要不变（`d0cf2b81741e1e51`，与这一轮开始的提交相同），逐个和批量两条入口都核对过。新测试 `test_unnormalized_leaves_match_normalized`：合成面板含 NaN、±inf、零、整数并列、布尔字段、长度 T 的市场序列（含 inf）和掩码，98 个表达式加 10 个专门让 ±inf 流进各类算子（`fill_nan`、`is_nan`、`where`、延迟、前填、相关、条件求和、截面秩、带行业和权重的中性化、市场序列、布尔字段）的表达式，逐字节比较「不改写」与「强制改写」（往 `BACKENDS` 塞一个不影响分派的键）两种结果，并核对字段作为结果时仍是 NaN。
- 变异检查（6 处，先跑对照）：根字段不改写、有缓存目录时也跳过缓存键、批量入口不标记根 —— 被抓到；Rust 里逐元素把 inf 当有效值、延迟把 inf 原样传出（各自重建扩展后跑）—— 被抓到，说明测试确实守住「内核把非有限当缺失」这条前提。整数叶子也不改写这一变异没被抓到：掩码外的行业值在内核里同样被掩码排除，结果相同；保守起见整数叶子仍照旧改写。
- 易用性：无接口变化。
- 未做 / 放弃：逐元素链融合（上面的估算，收益约 4%，代价是第二套逐元素实现）；输出缓冲复用（实测新分配不比复用慢）。

#### 复核后修补

- 把非有限值和掩码外当缺失，这条前提原来的测试只守住了一部分。复核发现：中性化用例的暴露和权重是同一个字段，权重的有限性检查顺带挡住了「暴露接受 inf」；`cs_zscore`/`cs_demean` 忽略输入掩码，只被原有的算子测试抓到。现在 `test_unnormalized_leaves_match_normalized` 改为：暴露和权重用不同字段（`high`/`volume`），另有一条不带权重的中性化，并直接对字段做 `cs_zscore`、`cs_demean`、`cs_scale`，这两条 Rust 变异都由本项测试抓到。
- 「配了 NumPy 分派时照旧改写」这个例外目前没有可观察的作用。复核把 16 个算子都配成 NumPy 分派，比较 15300 个结果，有没有这个例外都逐位相同，因为 NumPy 候选实现同样把 ±inf 当缺失，所以也没有测试能抓到去掉它的变异。保留它，是为了防将来新增的 NumPy 候选不按「非有限即缺失」处理：那时这个分支能保证改写照旧，代价只是配了分派时少一点优化。
