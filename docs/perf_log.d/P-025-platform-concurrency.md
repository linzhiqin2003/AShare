# P-025 平台调度共享线程预算与完整复测

- 提交：未提交（基于 `a5ea630`）。
- 手段：回测与统计使用同一个 Python 线程池，每次最多提交预算内的回测批次；完成回调
  先提交该变体的统计，再补下一批回测，避免把全部回测排在统计之前。
  原自动预算规则未改，依据下表保留变体上限 4、算子线程上限 8。
- 测量：15 核、24 GiB，NumPy 2.5.4。`bench/platform/grid.py` 调用现有 `speed.py`，
  按格旧版、新版交替，各一个新进程，冷运行一次后再跑三次取中位。所有配置均经过真实
  HTTP API、相同源表达式和两种中性化。以下单位秒，箭头前为冻结的 `a5ea630`。

单独开关调度（其他共享改动相同，自动 4×8，每进程冷运行一次后五次取中位）：

|---|---:|---:|

## 八组：四个窗口 × 两种中性化

| 并发变体 | 1 算子线程 | 4 算子线程 | 8 算子线程 |
|---|---:|---:|---:|
| 1 | 4.570 → 3.867 | 3.929 → 3.201 | 3.722 → 3.074 |
| 2 | 3.602 → 3.597 | 3.316 → 2.745 | 3.076 → 2.419 |
| 3 | 3.256 → 2.846 | 2.702 → 2.310 | 2.704 → 2.176 |
| 4 | 2.990 → 2.432 | 2.595 → 2.162 | 2.114 → 1.800 |
| 8（补测） | — | — | 2.317 → 2.080 |

2×1 的八组提升在噪声内；保留这个测点，不筛选成绩。3×4 对四组更好，4×8 对八组
吞吐更好。补测 8×8 没有继续加速，新版 RSS 7.58 GiB，高于自动配置的 5.06 GiB。
同一个池已在 Rust 内部并行，外部线程数不等于 CPU 核心数；输入扫描约 18 ms，
不能用 187 ms 的内核耗时直接断定是内存带宽瓶颈。

## 自动配置与内存

自动配置为 4×8，另起进程独立复测，故与手动表格有正常运行波动：

| 场景 | 之前 | 之后 | 协调进程峰值 RSS |
|---|---:|---:|---:|
| 四组 | 1.381 s | 1.285 s | 5.80 → 5.47 GiB |
| 八组 | 2.159 s | 1.759 s | 5.86 → 5.06 GiB |

省掉副本后仍有信号 mmap、IC 中间值与分配器高水位。串行八组、1 个算子线程时，
保留多个信号映射使 RSS 从 3.16 升至 3.64 GiB，不能宣称所有配置都降内存。
`ps` 进程树采样在当前环境不可用，表中只用工作进程自身 `ru_maxrss`，没有填造进程树值。

单组另用全新进程验证（IS 带子池＋验证，记录持仓）：只读预存信号为
**1.511 → 1.403 GB**；若先在同一进程求表达式，整体高水位为 **2.104 → 2.102 GB**。
前一个口径排除了表达式的历史高水位，不能当作完整研究进程的内存达标声明。

正确性：平台 4/8 组及调仓扫描的全部落盘数组、摘要 JSON 逐位比较；外部线程池的所有权、
完成回调、输出顺序、累计耗时均有测试。默认规则的现有并发测试继续通过。
原始结果在 `.cache/groupbt-fusion/grid/`、`grid-eight/` 与 `rss-*.json`；复跑命令见
`bench/groupbt/README.md`。主干配对表报告本轮所有共享改动的平台总体结果，
不将整段收益重复归给调度。
