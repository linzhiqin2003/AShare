### P-008 每日追加与读缓存：前缀索引、只读窗口内的快照

- 提交：`2856435`；复核后修补 `794869a`、`8882aa1`。
- 手段：数学算法（少做：不重复哈希、不读用不到的文件）。
- 改了什么：
  - **前缀索引**：缓存目录里新增 `.prefix-index`（npz，逐日「当天输入的独立摘要」和「前缀链摘要」各 32 字节，外加两者的 SHA-256 校验和）。
    前缀链本身（进入缓存键和元数据 `prefix_hash`）定义不变、顺序不变。下次运行先用线程池并行算每天输入的独立摘要（hashlib 释放 GIL），
    与索引一致的最长前缀直接沿用索引里的链摘要，从第一个不一致或新增的日期起才顺序重算链。**历史改写照样能发现**：任务书写的是
    「追加时只哈希新的一天」，但那样就不再核对历史输入（`model_series` 文档承诺「历史改写即便未更新 version 也不会命中旧缓存」），
    等于删掉一道校验；改为并行核对，顺序链只算新的一天。索引坏了、校验和不符或比输入短都当作没有索引。
  - **只读窗口内的快照**：先按键找出第一个未命中的日期 d；d 之前的日子不必重算，它们的状态只在 d 的估计窗口（最近 history 天）里用到，
    所以只读 [d − history, d) 这一段（d−1 读完整状态，更早的只读 f、残差、偏差三个字段，`ModelCache.load` 新增可选参数 `fields`），
    全部命中时只读要交给调用方的那几天。预读中发现快照损坏或被换掉，就把 d 提前到那一天重新计划；交出若干天之后才发现的，
    从那一天起重新计划（不重复交出）。
  - `start − 1` 那天的模型不再预先读（以前每次读缓存都会为它按需重建一次历史暴露、从头重放滚动描述子）；只有真要回归 `start` 当天时才读。
  - 最后一天的递推检查点改用 deflate 1（每次追加都要等它落盘，0.59 s → 0.36 s）。
  - 残差环形缓冲允许从窗口起点而不是第 0 天开始推入。

追加剩下的时间主要花在读窗口内的快照、并行核对全部输入摘要（改动前剖析约 0.4 s）和写检查点（0.36 s）上。

#### 一致性

两个配对场景每轮的最后一天 B、F、D、元数据逐位相同。全历史 4824 日重建与 P-007 逐日对比 B、F、D、元数据、`parameter_hash`：0 日不同（`perf_round.py diff`）。前缀链摘要定义未改，缓存键和 `prefix_hash` 不变，P-007 写下的缓存可直接沿用（首次运行补建索引）。

#### 测试与变异

新增 `test/risk/test_prefix_index.py`（8 个）：追加一天只重算一条链、改写历史某天的输入照样失效、索引损坏 / 校验和不符 / 比输入短都退回全量核对、较短的运行不截掉较长的索引、预读时发现损坏会提前起点、交出若干天后才发现损坏从该天重新计划且不重复交出、读缓存只打开窗口内的文件。`test_specific_incremental.py` 的窗口边界用例改为从窗口起点推入。
变异（`bench/risk/perf_mutations.py --only P-008`，先跑不改动的对照）：索引不核对逐日输入就沿用、不核对校验和、仍从第 0 天逐个读快照、预读失败不提前起点、交出之后发现损坏不重新计划、较短的运行截掉较长的索引——6 处全部被抓到。

#### 易用性

`model_series` 接口与默认行为不变。`ModelCache.load` 新增可选参数 `fields`；新增 `load_index()` / `save_index()`。缓存目录多一个隐藏文件 `.prefix-index`（`stats` 不计、`clear` 一起删）。

#### 试过放弃的

- 只哈希新的一天（任务书原写法）：追加还能再省约 0.4 s，但不再发现历史输入被改写，违背 `model_series` 的承诺，放弃。
- 把窗口内 252 天的历史状态并进检查点、追加时只开一个文件：能省掉多数快照读取，但检查点变大约 250 倍、每天都要重写，列为建议（见 `risk-suggestions.md`）。

#### 复核后修补（独立复核 P0-1、P1-3、P1-5）

- **交出的日子少了（P0-1）**：缓存部分命中时，主循环从窗口起点 `d − history` 开始，于是 `[start, d − history)` 这一段静默地没有交出。合成面板上本应 85 天，只交出 25 天；真实面板缓存到 4823 后，`start=0` 只交出约 1009 天。现在主循环从 `min(start, d − history)` 开始：窗口之前的日子在主循环里照常带模型读出并交出，这一段的读取省不掉；只有窗口之内、`start` 之前的日子才只预读部分字段。追加（`start = t − 1`）和读最后一天的路径没有变，所以上面的计时不受影响。
- **预读后发现快照坏了**：以前只在主循环起点大于 0 时才重新计划。如果坏的是第 `start` 天，而前一天只预读了部分字段，主循环会拿着缺字段的状态往下走。现在一律从坏掉的那一天起重新计划。
- **`fields` 参数**：拼错的字段名、空序列、字符串在读任何文件之前就报 ValueError。以前会被当成文件损坏，把完好的快照删掉。
- **逐日摘要的分段**：所有测试面板都短于 256 天，测不到分段边界。补了 600 天面板的测试，分别改写第 254、255、256、511、512、599 天，每一处都必须被发现。
- 新增测试在 `test/risk/test_review_fixes.py`，共 39 个：交出的日子覆盖 13 种「缓存到哪天 × start」组合，包括 start=0、在窗口外、在窗口内、等于第一个未命中日、全部命中、全部未命中，逐日与无缓存时逐位相同；坏快照 3 种；fork 2 个；写失败规则 5 个；队列上限、读前等待、证券表、fields（4 种）、翻比特、阈值闸、线程池关闭、长面板摘要、线程数、临时文件、类型校验（3 种）。
- 变异：`bench/risk/perf_mutations.py` 新增「复核修补」一组 22 处，包括复核人那边存活的 6 处，以及这次新写逻辑的反向改动。全部 51 处都被抓到；每组都先跑了不改动的对照，结束后源码恢复。脚本改为先把源码备份到 `.cache/perf_mutations/`，进程被杀后下次启动会先还原（复核 P2-9）。
- 重新验证，都在真实面板上，修补之后：
  - 最近 800 日：默认模式对从头算模式，B、F 每天逐位相同，D 最大相对差 8.75e-15，回退列占 0.055%（2341/4270483 个列日）；从头算模式对起点 eecf499，B、F、D 和元数据（不含 parameter_hash）800 日逐位相同；分段追加（500、501、503、512、530、600、700、760、790、800）后从第 0 天整段读出，与一次全量重建 800 日逐位相同，包括 parameter_hash。
  - 全历史 4824 日：全量重建与修补前（P-008 提交）逐日逐位相同；分段追加 11 段，跨过 1008/2016/3024 天的重锚点和多个块边界，最后从第 0 天整段读出 4824 天（同时验证了大规模下 P0-1 已修好），与全量重建逐日逐位相同。
- `bench/e2e` 风险阶段的结果摘要拆成 B、F、D、meta（不含 parameter_hash）、parameter_hash 五项，`compare.py` 会逐项写出哪几项相同、哪几项不同（复核 P2-3）。

#### 定向复核后的再修补（负责人）

- 上一节把「坏快照就重新计划」的条件放宽到任何 `day < miss` 之后，带出一个新问题：缓存对象打开之后某天的快照文件不见了（别的进程清理了目录，或 fork 出的子进程碰到父进程还没写完的日子），`load` 只返回 None、不注销这一天的登记，每次重新计划都回到同一天，最后 RecursionError。修补前是少交出日子，起点版是正常重算。
- 修法：`ModelCache.load` 发现文件不存在时注销这一天的登记（与文件损坏同样处理），重新计划后第一个未命中日就是这一天，其后的日子都重算，不再递归。
- 测试 6 个（`test_snapshot_removed_after_open_is_recomputed` 5 种形态：单个、多个、第 0 天、最后一天、全部命中后缺一天；`test_load_of_a_missing_snapshot_unregisters_the_day`）：修复前 6 个全部失败，修复后通过；重算的日子重新落盘，再读一遍全部命中，结果与无缓存逐位相同。
