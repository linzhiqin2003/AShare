## Rust 输出之外的状态

没有 Vec<Vec<f64>> 形式的全输出临时面板。列块只保存对最终输出每行的可变切片；并行块互不相交，所有源代码禁止 unsafe。

| 内核 | 主要状态与上界（不含输出；B 为列块宽，P 为同时运行块数） |
|---|---|
| delay/delta、逐元素 | O(1) 运算状态；Rayon 调度和线程池为常驻开销 |
| sum/mean/count/sumif | 32 B 字节状态/工作块；总峰值约 32·B·P，严重消去时另有每块 O(W) 浮点展开暂存，加输出切片索引 16·T·ceil(N/B) |
| std/var/zscore | 64 B 字节状态/工作块，加同一输出切片索引 |
| EMA/ffill | 24 B 字节状态/工作块，加切片索引 |
| decay | 64 B 字节状态/工作块，加切片索引 |
| 配对/高阶矩/回归 | 每列 5 或 4 个补偿矩、误差界、锚点、计数及常数运行长度；O(B·P)，没有整面板中间值 |
| min/max/arg/idx | 前一块后缀值、下标、有效数共 24·W·B，加当前前缀约 24·B；乘以 P，加切片索引 |
| rank/product | W·B 个 f64 环形状态，加每列计数；O(W·B·P) |
| median/quantile | 小窗口环形数据及固定有序缓冲各 W·B；长窗口 treap 每节点 6 个 8 字节字段；O(W·B·P) |
| MAD | W·B 环形数据及每工作块 W 项选择暂存；O(W·B·P) |
| 截面 | scale/demean/zscore 无掩码时仅标量状态；其余每线程 O(N) 暂存；中性化为 O(N·K+G·K)，不构造 N×G 行业哑变量 |
| CSR targets | 所有调仓日的选择向量目前保留候选容量，最坏约 8·D·N 字节，加每线程 O(N) 排序与 CSR Vec 增长容量；D 为调仓日数 |
| 因子自相关/换手 | 每工作块最多缓存 min(lag,32) 个 O(N) 排序/标签；大滞后不缓存整历史 |

上述是逻辑工作区公式，解释了 RSS 下界可能低估暂存的情况。默认线程下 B=ceil(N/P) 向上对齐 64，最大 1024；单线程也按最多 1024 列分块。无缺失/无掩码分支只省有效性判断，不改变加减顺序。

## 滑动求和的退化窗口与历史无关（2026-11-13）

### 两个复现走到哪里、为什么

- **整窗为 0 时的残差**（一列前 10 行正数、后 20 行全 0，窗口 12）：`ts_sum`、`ts_mean`、`ts_sumif` 都走 `time.rs` 的 `sum_rows`（窗口 > 0 的唯一路径，没有单独的快速或并行算术；并行只按列分块，每列算术相同）。增量补偿求和在大值离开窗口后留下 −6.8e-14 的残差。重建条件是 `8·ε·peak > 1e-11·(|和| + 1)`：峰值约 1000 时左边约 1.8e-12，右边因为 `+1` 的绝对下限是 1e-11，所以不触发；每 512 行的定期重建也没轮到。这个判据保证的是「相对 1 的绝对误差 ≤ 1e-11」，对恰为 0 的结果不构成保证。
- **同一组数给出不同的和**（6 个数、窗口 5，第 6 个等于第 1 个）：同一条增量路径，第 6 行的和是「第 5 行的和 − 离开值 + 进入值」，舍入取决于此前的累加历史，与逐窗口求和的次序不同，差 1 ulp。增量算法天然有这个性质，与重建判据无关。

### 同族算子现状（改动前）

在 40 行随机历史（含 1e7 量级）之后接一个退化窗口，各 200 次；「历史」一栏是同一个窗口接在 300 段不同历史之后得到的不同结果个数（1 = 只取决于窗口）。本表在返工时用改前构建重跑过，数字不变。

|---|---|---|---|---|

### 做法

- **A：退化窗口精确。** `sum_rows` 里加一个整数的「末尾连续相等长度」计数（与 `std_rows`、`Moments` 已有的同一个 `advance_run`）。计数 ≥ 有效个数时窗口内有效贡献全相等：和输出正确舍入的 `c·v`，均值输出 `v`，零一律输出正零。同时把增量状态重置为这个窗口的**精确和**：主和取舍入后的 `c·v`，补偿项取它的精确舍入误差（`fma(c, v, −c·v)`），峰值取 `|c·v|`。判定是整数比较，不依赖容差。`ts_count` 的贡献是 0/1 整数和，本来就精确，跳过这个判定。
  - 第一版把补偿项清零，丢掉了乘积的舍入误差：复核人的两个复现（`[1/3]×5 + [0]×4`，w=5；`[0.1]×20 + [0]×20`，w=20）在常数窗口之后变得比改前还差。改为补上 fma 余项后，两个复现与改前、与精确有理数都逐位相同，并由测试守住。
  - 曾试过「只在状态舍入不对时才重置」：变化的格子少约 2%，但常数窗口之后的状态取决于历史，不能保证随后的全 0 尾巴精确；也试过把重置挪到单独的一遍（只在有常数窗口的行执行，或只修被标记的格子），稀疏事件数据上慢 10–17%。最后保留在向量化的主循环里每格无分支地重置。
- **B：短窗口逐窗口直接求和，正确舍入。** 窗口 ≤ 3 时每行把窗口内的贡献按时间顺序一次算完（贡献只在进入时算一次，存在环形缓冲里；跨列向量化）：1 行原样；2 行只舍入一次，本来就是正确舍入；3 行用两次 TwoSum 加上误差项的 TwoSum，误差项相加若不精确（极少）就改算正确舍入的和。结果只取决于窗口，并且是正确舍入的。`ts_count` 的 0/1 和直接相加。
- **`exact=True`。** 每列把窗口和保存为一个无误差的浮点展开式（Shewchuk 的非重叠分量；进入、离开都是无误差变换），每行按 CPython `math.fsum` 的规则正确舍入。正确舍入的和只取决于窗口内数值的多重集合，所以与顺序、历史都无关。均值是这个正确舍入的和再除以个数（两次舍入，不是正确舍入的均值）；窗口全相等时恰为该值。部分和溢出时改用 2304 位定点整数累加（正负分开、最后一次舍入、偶数舍入），结果仍是正确舍入的和；只有精确和本身舍入后超出 float64 范围时才是 ±inf。下一行从窗口重建展开式。
  - 第一版溢出时退回普通和，`[1e308, 1e308, −1e308]` 得 inf；现在得 1e308，并在混合了最大值、1e308、2^970、次正规数的随机窗口上与精确有理数逐格相等。
- **参数检查。** `exact` 只接受 `bool` 和 `numpy.bool_`，其他类型报 `TypeError: exact must be a bool`。表达式层同样只收这两种（`numpy.bool_` 先转成 `bool`），`exact=False` 不进规范形式，`exact=True` 写成 `exact=True`；内置因子和普通表达式的文本与摘要与主干逐个相同（17 个，含 ts_sum、ts_mean、ts_sumif 的探针）。

K = 3 沿用第一轮的选择：第一轮原型里逐窗口直接求和在 w = 4、5 时已慢于增量；这次把短窗口改成单遍计算后，w ≤ 3 反而比改前快（下表）。

### 已有输出的变化

用复核人的随机语料（多段常数、常数接 0、常数接小数，10 种窗口 × min_periods × 有无掩码）与改前构建逐格比较，参照精确有理数：

| 路径 | 算子 | 变化的格子 | 改后更近 | 改前更近 | 一样近 |
|---|---|---:|---:|---:|---:|
| w ≤ 3 | sum / mean / sumif | 191,203 / 188,955 / 124,056 | 全部 | 0 | 0 |
| w > 3 | sum | 182,423 | 163,613 | 8,605 | 10,205 |
| w > 3 | mean | 183,453 | 166,149 | 9,945 | 7,359 |
| w > 3 | sumif | 196,206 | 181,620 | 6,504 | 8,082 |

- w ≤ 3 的默认路径现在逐格是正确舍入的（改前有 191,203 格不是）。
- w > 3「改前更近」的格子（上表三项共 25,054 格；分类脚本把均值按「精确和 ÷ 个数」比较，数出 27,321 格），每一格在同一个 512 行重建块里、在它之前都有一个常数窗口（含只有一个有效值的窗口），也就是状态在那里被重置成了精确和；之后的增量误差从这个新起点重新累积，最后一位随之换成另一种取值，有时离精确值远几个 ulp（1–3 ulp 占 63%）。按 `|误差| / (|精确值| + 1)` 计，改后最大 1.07e-12，改前 1.25e-12；常数窗口给错值的格子（sum / mean / sumif）从 62,142 / 64,189 / 73,346 格降到 0。所以不能说「变化的格子都更接近精确值」，只能说大多数更近，更远的都来自状态重置后重新累积的末位差别，且不超过原有误差界。
- 真实面板上（主目录 `data/` 只读，内置因子库 14 个因子新旧构建各算一次）：12 个逐位相同。`amihud_20` 有 223,090 / 15,341,895 格不同，全部与精确有理数比较：改后更近 189,034 格、改前更近 33,608 格、一样近 448 格；最大相对误差改前 3.0e-12、改后 2.0e-14；33,608 格都在同一重建块里有更早的常数窗口（零收益日）。`amount_20` 有 2,828 格不同：改后更近 2,325、改前更近 480、一样近 23，最大相对误差改前 1.2e-15、改后 6.3e-16，同样都能这样解释。 这组「更近 / 更远 / 一样近」的格数以「精确有理数的和再除以个数」为参照；独立复核用「`fsum` ÷ 个数」作参照得到 188,281 / 28,946 / 5,863，口径不同、结论一致。
- 因子缓存：键里含 `panelops.build_id`，它由 Rust 内核源码的哈希生成，已随改动变化，旧缓存不会被读到。
- `bench/e2e/results/baseline.json` 与 `round1-after.json` 是历史测量记录，里面因子阶段的 `amihud_20`、`amount_20` 摘要与新构建不同，没有改写；下次 `make perf-compare` 会把这两项报为「不同」，原因即上一条。
- 仓库里没有其他逐位冻结的 panelops 输出（测试里的期望值都来自独立参考或精确有理数）。
